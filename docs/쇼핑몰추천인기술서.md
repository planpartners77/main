# 쇼핑몰 추천인(레퍼럴) 프로그램 기술서

> 목적: "고유 추천 링크 + UTM 파라미터 + 쿠키를 결합해 정확한 전환을 추적한다"는 설계를
> 다른 프로젝트(쇼핑몰/서비스 사이트)에도 그대로 이식할 수 있도록, 이번 PlanPartners
> 구현(2026-09-09, commit `d41e05d`, `40dbc21`)의 스키마·코드·설계 이유를 정리한다.
> 코드 스니펫은 Next.js(App Router) + Supabase(Postgres+RLS) 기준이지만, 구조 자체는
> 프레임워크에 무관하게 적용 가능하다.

---

## 1. 핵심 설계 원칙

1. **추천 코드(코드 자체)와 UTM(유입 채널 태그)은 서로 다른 축이다.**
   - 추천 코드 = "누구 추천으로 왔는가" (파트너/회원 단위, 정산·트리 구조와 연결)
   - UTM = "어느 채널로 왔는가" (카카오톡/블로그/문자/광고 등, 마케팅 채널 성과 분석용)
   - 두 값을 하나의 링크에 같이 실어 보내되(`?ref=CODE&utm_source=...`), 저장/조회는
     별도 값으로 다뤄야 "같은 파트너인데 어느 채널이 더 잘 전환되는가"를 답할 수 있다.
2. **클릭 시점의 값을 쿠키+localStorage에 이중 저장**하고, 실제 전환(가입/신청) 시점에는
   "그 값을 다시 계산하지 않고 저장해둔 값을 그대로 사용"한다. 클릭과 전환 사이에는
   보통 페이지 이동이 여러 번 일어나므로 URL 파라미터만으로는 끝까지 못 따라간다.
3. **서버는 클라이언트가 보낸 값을 그대로 믿지 않는다.** 특히 정산(돈)과 연결되는 추천
   코드는 서버에서 재조회(존재 여부, 활성 여부, 만료 여부)한 뒤에만 기록한다. UTM처럼
   순수 통계용 값은 재검증 없이 그대로 저장해도 무방하다(위조되어도 금전적 피해 없음).
4. **"전환"은 한 종류가 아니다.** 최소 3단계로 나눠서 각각 기록한다.
   - 클릭(click) — 링크를 눌러 사이트에 들어옴
   - 리드/가입(lead, registration) — 폼 제출 또는 회원가입
   - 완료/매출(completed, purchase) — 실제 매출·구독 확정 (이 사이트는 결제가
     사이트 밖(제휴사)에서 일어나므로 "관리자가 리드 상태를 완료로 바꾸는 시점"을
     매출 확정의 대리 지표로 삼았다 — §7 참고)
5. **어트리뷰션 정책(귀속 기준)을 명시적으로 정한다.** 한 방문자가 여러 추천 링크를
   클릭할 수 있다 — "최초 클릭을 인정할지(first-touch) / 마지막 클릭을 인정할지
   (last-touch)"는 파트너 정산액에 영향을 주는 비즈니스 정책이므로, 코드를 짜기 전에
   반드시 정하고 주석으로 남긴다. 이번 구현은 **last-touch**(재방문 시 새 값이 있으면
   덮어씀)를 택했다.

## 2. 전체 흐름

```
[파트너/회원] 링크 생성 시 코드 발급 → 링크에 ref + utm 파라미터를 함께 붙여서 공유
        │
        ▼
[방문자] 링크 클릭 → 사이트 진입 시 최상위 레이아웃에서 캡처 컴포넌트가 실행
        │  - ref 값 → /api/referral(type=click)로 서버에 클릭 기록 + codeId 확인
        │  - utm_* 값 → 그대로 클라이언트 저장(서버 검증 불필요)
        ▼
[저장] 쿠키(30일) + localStorage(30일, 백업용) 이중 저장
        │  - Safari ITP 등으로 localStorage가 지워져도 쿠키로 폴백
        ▼
[전환 시점 A] 회원가입 폼 제출 → 저장된 ref 코드 문자열을 가입 요청에 실어 보냄
        │  → 서버(트리거/함수)가 코드 유효성 재검증 후 전환 기록
        ▼
[전환 시점 B] 리드(상담/신청) 폼 제출 → 저장된 codeId + utm_* 값을 leads row에 직접 기록
        │  → 리드 insert 직후 /api/referral(type=convert)로 리드 전환 기록
        ▼
[전환 시점 C] 관리자가 리드 상태를 "완료"로 변경(=매출/구독 확정)
        │  → referral_conversions에 최종 전환(conversion_type='completed') 기록
        ▼
[집계] 관리자 페이지에서 코드별 클릭수/가입수/리드수/완료수 + 채널(utm_medium)별 분포 표시
```

## 3. DB 스키마

### 3-1. 추천 코드/클릭/전환 (핵심 3테이블)

```sql
create table referral_codes (
  id uuid primary key default gen_random_uuid(),
  code text unique not null,               -- 사람이 읽는 코드 문자열 (예: PARTNER001)
  name text,                                -- 파트너/회원 이름 (표시용)
  type text check (type in ('partner', 'member')),
  parent_code_id uuid references referral_codes(id),   -- 다단계 추천 트리용(선택)
  root_code_id uuid references referral_codes(id),     -- 트리의 최상위 코드(집계용)
  depth int default 0,
  total_clicks int default 0,               -- 카운터 컬럼(빠른 조회용, §6 참고: 신뢰 X)
  total_registrations int default 0,
  is_active boolean default true,
  expires_at timestamptz,
  created_at timestamptz default now()
);

create table referral_clicks (
  id bigint generated always as identity primary key,
  code_id uuid references referral_codes(id),
  ip text,
  user_agent text,
  session_id text,
  created_at timestamptz default now()
);

-- conversion_type은 의도적으로 CHECK 제약을 걸지 않은 순수 text로 둔다.
-- 나중에 'completed'처럼 새 전환 단계를 추가할 때 마이그레이션 없이 확장 가능하게 하기 위함.
create table referral_conversions (
  id bigint generated always as identity primary key,
  code_id uuid references referral_codes(id),
  root_code_id uuid references referral_codes(id),
  lead_id uuid references leads(id),
  conversion_type text,   -- 'registration' | 'lead' | 'completed' (자유 확장 가능)
  depth int,
  created_at timestamptz default now()
);
```

**RLS 정책 원칙**:
- `referral_codes` / `referral_clicks` / `referral_conversions` → **관리자만 select**
  (일반 사용자·비회원에게 추천 코드 목록이나 집계를 노출할 이유가 없음).
- `referral_clicks` insert / 카운터 증가는 **anon에게 열지 않고, 서버 라우트가 서비스
  롤 키(RLS 우회)로만 처리**한다 (§5).
- 카운터 증가 함수는 원자적 UPDATE 한 줄짜리 SQL 함수로 만들고 `revoke execute ... from public`
  으로 anon/authenticated 실행 권한을 명시적으로 제거한다 — 서비스 롤 키 호출로만 열어둠.

```sql
create policy "referral_codes_admin_all" on referral_codes
  for all using (exists (select 1 from admin_users where admin_users.id = auth.uid()))
  with check (exists (select 1 from admin_users where admin_users.id = auth.uid()));
-- referral_clicks / referral_conversions 도 동일 패턴

create function increment_referral_click(p_code_id uuid) returns void as $$
  update referral_codes set total_clicks = total_clicks + 1 where id = p_code_id;
$$ language sql;
revoke execute on function increment_referral_click(uuid) from public;
```

### 3-2. 리드(신청/상담) 테이블에 채널 컬럼 얹기

리드·신청 기록이 있는 서비스라면, 처음부터 리드 테이블에 UTM 컬럼을 넣어두는 것이
좋다(나중에 추가하면 과거 데이터는 채울 수 없음).

```sql
alter table leads add column referral_code_id uuid references referral_codes(id);
alter table leads add column utm_source text;
alter table leads add column utm_medium text;
alter table leads add column utm_campaign text;
alter table leads add column referrer_url text;  -- document.referrer/현재 URL (보조 디버깅용)
```

> **재사용 체크포인트**: 새 프로젝트라면 이 4개 컬럼을 처음부터 만들되, "만들기만 하고
> 채우는 코드를 안 짜는" 실수를 조심할 것 — 이번 세션에서 실제로 벌어졌던 문제였다
> (컬럼은 초기 스키마부터 있었는데 1년 가까이 아무도 값을 넣지 않고 있었음).

## 4. 클라이언트 캡처/저장 로직

핵심 유틸(`lib/referral/client.ts`)은 순수 함수 모음으로, 프레임워크 의존성이 없어
그대로 복붙 이식 가능하다.

```typescript
const STORAGE_KEY = "pp_ref";
const COOKIE_KEY = "pp_ref_code";
const UTM_STORAGE_KEY = "pp_utm";
const UTM_COOKIE_KEY = "pp_utm";
const TTL_DAYS = 30; // 쿠팡파트너스 등 업계 관행과 유사하게 30일. 사업 특성에 맞게 조정.

export interface StoredReferral {
  codeId: string;   // 서버가 확인해준 UUID (leads.referral_code_id 등 FK로 바로 씀)
  code: string;     // 사람이 읽는 코드 문자열 (회원가입 폼에 그대로 실어보냄)
}

export interface StoredUtm {
  utm_source: string | null;
  utm_medium: string | null;
  utm_campaign: string | null;
}

// Safari ITP 등으로 localStorage가 지워지거나 접근 불가한 경우를 대비해 쿠키에도
// 함께 저장한다(이중화). try/catch로 감싸는 이유: 프라이버시 모드에서 storage 접근
// 자체가 예외를 던질 수 있음 — 실패해도 사이트 이용에는 지장이 없어야 한다.
function setCookie(name: string, value: string, days: number) {
  try {
    const maxAge = days * 24 * 60 * 60;
    document.cookie = `${name}=${encodeURIComponent(value)}; max-age=${maxAge}; path=/; samesite=lax`;
  } catch {}
}

function getCookie(name: string): string | null {
  try {
    const match = document.cookie.match(new RegExp(`(?:^|; )${name}=([^;]*)`));
    return match ? decodeURIComponent(match[1]) : null;
  } catch {
    return null;
  }
}

// 클릭 발생 시 호출. 서버에 클릭을 기록하고, 서버가 확인해준 codeId를 돌려받은
// "이후에만" 저장한다 — 존재하지 않거나 만료된 코드를 클라이언트가 계속 우기며
// 저장하는 일을 막기 위함(서버가 진실의 원천).
export function recordReferralClick(code: string) {
  fetch("/api/referral", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ type: "click", code }),
  })
    .then((res) => (res.ok ? res.json() : null))
    .then((data: { codeId?: string } | null) => {
      if (!data?.codeId) return;
      try {
        localStorage.setItem(STORAGE_KEY, JSON.stringify({ codeId: data.codeId, code, savedAt: Date.now() }));
      } catch {}
      setCookie(COOKIE_KEY, code, TTL_DAYS);
    })
    .catch(() => {});
}

export function getStoredReferral(): StoredReferral | null {
  try {
    const raw = localStorage.getItem(STORAGE_KEY);
    if (!raw) return null;
    const parsed = JSON.parse(raw) as StoredReferral & { savedAt: number };
    if (Date.now() - parsed.savedAt > TTL_DAYS * 24 * 60 * 60 * 1000) {
      localStorage.removeItem(STORAGE_KEY);
      return null;
    }
    return { codeId: parsed.codeId, code: parsed.code };
  } catch {
    return null;
  }
}

// 회원가입 시 사용할 추천코드 문자열. localStorage(codeId까지 확인된 값)를 우선하고,
// 없으면 쿠키(코드 문자열만 있음 — 가입 시점에 서버가 다시 유효성 검증)로 폴백한다.
export function getReferralCodeForSignup(): string | null {
  const stored = getStoredReferral();
  if (stored?.code) return stored.code;
  return getCookie(COOKIE_KEY);
}

// 추천 링크(?ref=)뿐 아니라 순수 광고/캠페인 링크(?utm_source=...)로 유입된 경우도
// 잡을 수 있도록, ref와 별개로 utm_* 파라미터를 캡처한다. UTM은 금전과 무관한 통계용
// 값이라 서버 왕복 없이 클라이언트에서 바로 저장한다(click과의 차이).
export function captureUtmFromUrl(search: string) {
  const params = new URLSearchParams(search);
  const value: StoredUtm = {
    utm_source: params.get("utm_source"),
    utm_medium: params.get("utm_medium"),
    utm_campaign: params.get("utm_campaign"),
  };
  if (!value.utm_source && !value.utm_medium && !value.utm_campaign) return;

  try {
    localStorage.setItem(UTM_STORAGE_KEY, JSON.stringify({ ...value, savedAt: Date.now() }));
  } catch {}
  setCookie(UTM_COOKIE_KEY, JSON.stringify(value), TTL_DAYS);
}

export function getStoredUtm(): StoredUtm | null {
  try {
    const raw = localStorage.getItem(UTM_STORAGE_KEY);
    if (raw) {
      const parsed = JSON.parse(raw) as StoredUtm & { savedAt: number };
      if (Date.now() - parsed.savedAt <= TTL_DAYS * 24 * 60 * 60 * 1000) {
        return { utm_source: parsed.utm_source, utm_medium: parsed.utm_medium, utm_campaign: parsed.utm_campaign };
      }
      localStorage.removeItem(UTM_STORAGE_KEY);
    }
  } catch {}

  try {
    const cookieVal = getCookie(UTM_COOKIE_KEY);
    if (cookieVal) return JSON.parse(cookieVal) as StoredUtm;
  } catch {}
  return null;
}
```

> **주의(last-touch 정책)**: `recordReferralClick`/`captureUtmFromUrl` 모두 새 값이
> 있으면 기존 저장값을 덮어쓴다. "최초 유입 파트너에게만 정산해야 한다"는 정책이라면
> "이미 저장된 값이 있으면 덮어쓰지 않음(first-touch)"으로 뒤집어야 한다 — 이 한 줄
> 차이가 파트너 정산 분쟁으로 이어질 수 있으니 기획팀과 반드시 확인 후 결정할 것.

### 4-1. 캡처 컴포넌트 (최상위 레이아웃에 마운트)

```tsx
"use client";
import { useEffect } from "react";
import { recordReferralClick, captureUtmFromUrl } from "@/lib/referral/client";

export function ReferralCapture() {
  useEffect(() => {
    const code = new URLSearchParams(window.location.search).get("ref");
    if (code) recordReferralClick(code);
    captureUtmFromUrl(window.location.search);
  }, []);

  return null;
}
```

이 컴포넌트를 사이트 전체 레이아웃(`app/(site)/layout.tsx` 등)에 한 번만 마운트하면
어느 페이지로 들어오든(홈이 아니어도) 파라미터를 캡처한다. **중요**: 랜딩 페이지에만
넣지 말 것 — 딥링크(예: 특정 상품 상세페이지로 바로 오는 광고)도 캡처해야 한다.

## 5. 링크 클릭 기록 / 전환 기록 서버 API

```typescript
// app/api/referral/route.ts
export async function POST(request: Request) {
  const body = await request.json();
  const supabase = createAdminClient(); // 서비스 롤 키 — RLS 우회

  if (body.type === "click") {
    const code = body.code?.trim();
    const { data: referral } = await supabase
      .from("referral_codes")
      .select("id, is_active, expires_at")
      .eq("code", code)
      .maybeSingle();

    // 서버가 코드 존재/활성/만료를 재검증 — 클라이언트가 조작한 코드 문자열을
    // 그대로 믿고 저장하지 않는다.
    if (!referral || !referral.is_active || (referral.expires_at && new Date(referral.expires_at) < new Date())) {
      return NextResponse.json({ ok: false }, { status: 404 });
    }

    await supabase.from("referral_clicks").insert({ code_id: referral.id, user_agent: request.headers.get("user-agent") });
    await supabase.rpc("increment_referral_click", { p_code_id: referral.id });
    return NextResponse.json({ ok: true, codeId: referral.id }); // 클라이언트는 이 codeId만 저장
  }

  if (body.type === "convert") {
    const { leadId, codeId } = body;
    // leadId에 실제로 codeId가 붙어 있는지 DB에서 재확인 — 클라이언트가 아무 codeId나
    // 보내 남의 리드를 자기 추천으로 가로채는 것을 막는다.
    const { data: lead } = await supabase.from("leads").select("id, referral_code_id").eq("id", leadId).maybeSingle();
    if (!lead || lead.referral_code_id !== codeId) return NextResponse.json({ ok: false }, { status: 404 });

    const { data: referral } = await supabase.from("referral_codes").select("id, root_code_id, depth").eq("id", codeId).maybeSingle();
    if (!referral) return NextResponse.json({ ok: false }, { status: 404 });

    await supabase.from("referral_conversions").insert({
      code_id: referral.id, root_code_id: referral.root_code_id, lead_id: leadId,
      conversion_type: "lead", depth: referral.depth,
    });
    await supabase.rpc("increment_referral_conversion", { p_code_id: referral.id });
    return NextResponse.json({ ok: true });
  }

  return NextResponse.json({ ok: false }, { status: 400 });
}
```

**왜 서비스 롤 키를 쓰는가**: 클릭/전환 테이블은 관리자만 select할 수 있게 RLS를
걸어뒀는데, 클릭은 로그인 전 익명 사용자도 발생시켜야 한다. "익명도 insert는 가능"
하도록 RLS를 여는 대신, RLS를 완전히 잠근 채로 서버 라우트가 서비스 롤 키로 우회
insert하는 쪽을 택했다 — 이렇게 하면 (1) anon 사용자가 직접 테이블에 아무 값이나
insert하는 것을 막고, (2) 서버 코드 한 곳에서만 유효성 검증 로직을 관리할 수 있다.

## 6. 신청/가입 폼에서의 사용 패턴

```typescript
// 신청 폼 제출 시
const referral = getStoredReferral();   // { codeId, code } | null
const utm = getStoredUtm();             // { utm_source, utm_medium, utm_campaign } | null

const { error } = await supabase.from("leads").insert({
  // ...폼 필드...
  referral_code_id: referral?.codeId ?? null,
  utm_source: utm?.utm_source ?? null,
  utm_medium: utm?.utm_medium ?? null,
  utm_campaign: utm?.utm_campaign ?? null,
  referrer_url: typeof window !== "undefined" ? window.location.href : null,
});

// insert 성공 후, 추천 코드가 있었다면 리드 전환도 별도로 기록
if (referral) {
  fetch("/api/referral", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ type: "convert", leadId, codeId: referral.codeId }),
  }).catch(() => {}); // fire-and-forget: 실패해도 신청 자체는 이미 접수 완료
}
```

**회원가입은 다른 경로를 탄다**: 회원가입은 보통 DB 트리거(`handle_new_user` 같은)로
처리되므로, 클라이언트는 `getReferralCodeForSignup()`으로 얻은 **코드 문자열**을
가입 요청의 `user_metadata`(또는 별도 파라미터)에 실어 보내고, 트리거가 서버 측에서
그 코드를 다시 조회해 유효성을 검증한 뒤 `referral_conversions(conversion_type='registration')`
를 기록한다. 클라이언트가 codeId(UUID)를 미리 알아도 트리거 안에서는 문자열 코드로
다시 조회하는 편이 안전하다(가입 시점 최신 상태 반영).

## 7. "구매/매출 확정" 전환을 어디에 훅킹할지 판단하는 법

결제 게이트웨이가 사이트 안에 있는 일반 쇼핑몰이라면 결제 완료 콜백/웹훅에서
`referral_conversions(conversion_type='purchase')`를 기록하면 된다. 하지만
**결제가 사이트 밖(오프라인 계약, 제휴사 콜센터, 별도 청구 시스템 등)에서 일어나는
비즈니스**라면 "이 시점을 매출 확정으로 본다"를 코드로 지정해야 한다. 이번 프로젝트는
관리자가 리드 상태를 `completed`로 바꾸는 순간(정산 대상이 되는 시점)을 그 대리
지표로 삼았다.

```typescript
// 관리자가 리드 상태 select를 바꿀 때 (client component, 관리자 세션이라 RLS 통과)
async function recordCompletionConversion(supabase, leadId: string, referralCodeId: string | null) {
  if (!referralCodeId) return;

  // 중복 방지: 이미 이 리드에 대한 완료 전환이 기록돼 있으면 다시 넣지 않는다.
  // (관리자가 상태를 완료→취소→완료로 왔다갔다 해도 전환 집계가 중복 카운트되지 않게)
  const { data: existing } = await supabase
    .from("referral_conversions").select("id")
    .eq("lead_id", leadId).eq("conversion_type", "completed").maybeSingle();
  if (existing) return;

  const { data: referral } = await supabase
    .from("referral_codes").select("id, root_code_id, depth").eq("id", referralCodeId).maybeSingle();
  if (!referral) return;

  await supabase.from("referral_conversions").insert({
    code_id: referral.id, root_code_id: referral.root_code_id,
    lead_id: leadId, conversion_type: "completed", depth: referral.depth,
  });
}
```

**일반화 지침**: "이 프로젝트에서 100% 확정 매출로 볼 수 있는 상태 전이가 무엇인가"를
먼저 찾는다. 후보는 보통 이 중 하나다.
- 결제 성공 웹훅/콜백 (온라인 결제형 쇼핑몰)
- 주문 상태가 `paid`/`confirmed`로 바뀌는 순간 (구매확정형)
- 정산 테이블에 행이 생기거나 `approved`/`paid`로 바뀌는 순간 (이번 케이스처럼
  결제가 외부에서 일어나는 리드/중개형 비즈니스)
- 구독이 활성화되는 순간 (SaaS/멤버십형)

찾았다면 그 지점 **딱 한 곳**에만 훅을 걸고, 반드시 `lead_id`(또는 `order_id`) 기준
중복 방지 체크를 넣는다 — 상태가 여러 번 바뀔 수 있는 시스템에서는 중복 삽입이
가장 흔한 버그다.

## 8. 관리자 대시보드 집계 패턴

- **카운터 컬럼(`total_clicks` 등)을 그대로 믿지 말고, 로그 테이블에서 재집계해서
  화면에 보여준다.** 카운터는 표시 속도를 위한 캐시일 뿐, 정합성 문제(중복 실행,
  트랜잭션 실패 등)가 생겼을 때 로그 테이블(`referral_clicks`/`referral_conversions`)이
  항상 진실이다.

```typescript
const [{ data: clicksData }, { data: conversionsData }] = await Promise.all([
  supabase.from("referral_clicks").select("code_id").in("code_id", codeIds),
  supabase.from("referral_conversions").select("code_id").in("code_id", codeIds).eq("conversion_type", "registration"),
]);
// JS Map으로 code_id별 count() — 코드 몇십~몇백 개 규모라면 SQL GROUP BY 뷰/함수를
// 새로 안 만들어도 이 정도로 충분하고, 스키마 변경이 필요 없다는 장점이 있다.
```

- **채널(UTM)별 분포**는 `leads.utm_medium`을 `referral_code_id`로 묶어 집계한다.
  단, 리드 테이블의 RLS가 "담당 카테고리 관리자만 조회"처럼 스코프가 좁게 걸려 있는
  프로젝트라면, 이 채널 집계도 그 스코프 안에서만 계산된다 — super_admin이 아닌
  일반 관리자에게는 부분치일 수 있다는 점을 화면 주석/툴팁으로 명시해야 한다.

## 9. 새 프로젝트에 이식할 때 체크리스트

1. `referral_codes` / `referral_clicks` / `referral_conversions` 3테이블 생성 + RLS
   (관리자만 select, insert/update는 서비스 롤 경유).
2. 리드·주문 테이블에 `referral_code_id`, `utm_source`, `utm_medium`, `utm_campaign`
   컬럼을 **처음부터** 넣는다(나중에 추가하면 과거 데이터 소급 불가).
3. `lib/referral/client.ts` 그대로 복사 — 쿠키 키 이름(`pp_ref` 등 사이트별 prefix)만
   바꾼다.
4. 최상위 레이아웃에 `<ReferralCapture />` 마운트.
5. 링크 생성 UI(관리자 코드관리 화면, 회원 마이페이지 등)에서 `?ref=`뿐 아니라
   `utm_source/medium/campaign`을 항상 같이 붙이도록 통일.
6. 모든 리드/주문 폼 제출 코드에 `getStoredReferral()` + `getStoredUtm()` 값을
   insert 페이로드에 채운다.
7. 회원가입 트리거(또는 가입 서버 로직)에서 추천 코드 문자열을 재검증 후
   `conversion_type='registration'` 기록.
8. **이 프로젝트에서 "매출 확정"에 해당하는 단 하나의 상태 전이 지점을 찾아** 그
   곳에만 `conversion_type='completed'`(또는 `'purchase'`) 기록 로직을 훅킹하고,
   `lead_id`/`order_id` 기준 중복 방지 체크를 반드시 넣는다.
9. 어트리뷰션 정책(first-touch/last-touch)을 기획팀과 확정하고 코드 주석에 명시.
10. 관리자 화면에 코드별 클릭/가입/리드/완료 수 + 채널별 분포를 재집계 방식으로 노출.

## 10. 자주 하는 실수 (이번 세션에서 실제로 겪은 것 포함)

- **컬럼만 만들고 채우는 코드를 안 짜는 것** — `leads.utm_*` 컬럼이 초기 스키마부터
  있었는데 어떤 폼도 값을 넣지 않아 계속 비어 있었다. 컬럼 추가 PR과 "그 컬럼을 채우는
  코드"는 항상 같은 PR에서 같이 검증할 것.
- **재조사 없이 예전 조사 결과를 신뢰하는 것** — 사전 조사에서 "리드 전환 API가
  죽어있다(호출하는 코드가 없다)"고 나왔지만, 실제 파일을 열어보니 이미 정상 호출되고
  있었다. 자동화된 코드베이스 탐색 결과라도 실제 수정 전에는 반드시 대상 파일을 직접
  열어 재확인할 것.
- **완료 전환 기록에 중복 방지 체크를 안 넣는 것** — 상태값을 왔다갔다 바꿀 수 있는
  관리자 UI에서는 필수. 없으면 파트너 정산액이 실제보다 부풀려진다.
- **어트리뷰션 정책을 코드에 은연중에 박아놓고 아무도 모르는 것** — "새 클릭이 있으면
  덮어쓴다"는 last-touch 정책이 파트너 정산 분쟁이 생기기 전까지 아무 문서에도 안
  적혀 있는 경우가 많다. 이 문서의 §1-5, §4 경고문처럼 반드시 명시할 것.
